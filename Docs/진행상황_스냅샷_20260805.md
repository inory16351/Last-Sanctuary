## 0. 문서 관리 원칙 (필독 — 모든 세션이 지킬 것)

이 문서(`진행상황.md`)는 **이 파일 하나만 읽으면 어떤 새 대화·다른 에이전트라도 지금까지의 작업을 파악하고 바로 이어서 작업할 수 있어야 한다**는 목적으로 존재한다. 2026-08-05에 이 원칙이 실제로 깨진 사고가 있었다(15절 참조 — 1~19절이 통째로 사라진 채로 발견됨). 아래 세 가지를 반드시 지킬 것.

1. **작업을 시작하기 전, 이 문서 전체를 읽을 것.** 일부만(예: 요약 표만) 보고 판단하지 말 것 — 각 절의 "⚠️"/"아직 확인 못 한 것" 항목에 다음 작업에 영향을 주는 제약이 들어있는 경우가 많다.
2. **작업을 끝낼 때(또는 대화가 끝나기 전) 반드시 이 문서를 갱신할 것.** 새로 한 작업은 번호를 이어서 새 절로 추가하고(무엇을/왜/어떻게, 겪은 함정, 아직 확인 못 한 것 — 기존 절들의 형식을 따를 것), 상단 "지금까지 만든 것" 표와 맨 위 "마지막 갱신" 날짜도 같이 갱신한다. **다음 세션이 이 파일만 보고 이어갈 수 있어야 갱신한 것이다** — 대화창에만 설명하고 문서에 안 남기면 안 한 것과 같다.
3. **완료된 작업이라도 절을 임의로 삭제하지 말 것.** 이 문서는 "지금 뭐가 남았는지"만 보는 목록이 아니라 **게임 구조 전체를 파악하기 위한 기록**이다 — 왜 이렇게 만들었는지(예: 4절의 정수화 이유, 6절의 타겟 우선순위 버그, 13절의 벽 충돌 방식)를 모르면 다음 작업에서 같은 실수를 반복하거나 기존 설계를 실수로 깨뜨리기 쉽다. 시스템을 갈아엎었으면 **기존 절은 남기고 새 절을 추가**해서 "X절 참조, 이렇게 바뀜/대체됨"이라고 링크할 것. 오타·사실관계 오류를 바로잡는 건 삭제가 아니라 괜찮다 — 금지되는 건 **이미 끝난 작업 기록 자체를 통으로 들어내는 것**이다.

## 3. 맵 생성 (`MapGenerator` / `MapGenerationConfigSO`)

**파이프라인**: 청크별 바이옴 추첨(시드 결정적) → 바닥 채우기 → 장애물 마스크(펄린 노이즈, 바이옴별 백분위 임계값) → 셀룰러 오토마타 스무딩 → 넥서스 반경/경계벽/스폰게이트 강제 반영 → 스폰게이트→넥서스 통로 굴착 → **BFS 연결성 검사(고립 지역 자동 벽 처리)** → SetTilesBlock 일괄 기록.

- **맵 크기 지정 2방식**: `Chunks`(청크개수×청크크기) / `Tiles`(원하는 타일 수 직접 입력 → 청크 배수로 올림 생성 후 경계 초과분 잘라내기, 정확한 크기 보장).
- **카메라 경계 자동 동기화**: 생성 시 `MapBounds` 콜라이더를 맵 크기에 맞게 재설정 + `CinemachineConfiner2D.InvalidateBoundingShapeCache()` 자동 호출.
- **현재 설정값** (`MapGenConfig.asset`): `sizeMode: Tiles`, **맵 크기 320×320**, 청크 20×20, 넥서스 클리어 반경 6, 스폰게이트 폭 6.
- 바이옴 2종: `Biome_Vessel`(혈관 지대, 벽밀도 0.18), `Biome_Necrotic`(괴사 지대, 벽밀도 0.26).
- 인스펙터에 생성 버튼(현재 시드로/새 시드로/전부 지우기) 있음. Ctrl+Z 지원.

**맵 크기 320×320 vs 몬스터 이동속도** (기존 ⚠️ → 완화됨):
스폰 지점~넥서스 거리 160타일, 몬스터 이동 2.2타일/s(14절부터 근거리·원거리 동일) → 도달까지 약 73초.
**웨이브 타이머가 "첫 전투 시점"부터 시작하도록 설계했기 때문에(11절) 진군 시간이 전투 시간을 깎아먹지는 않는다.**

## 4. 능력치 & 전투 수식 (`BalanceConfigSO`)

원본 근거는 `프로토 타입 캐릭터 생성 규칙.md` — **이 md를 먼저 참고할 것**. 기획서 원문(14능력치)이 아니라 **프로토타입 전용 4능력치 체계**(체력/공격력/방어력/체력회복력, 1~100 척도, 생성시 1~10 랜덤)로 구현되어 있음.

**⚠️ 2026-08-04 개정 — 모든 치환값이 정수로 떨어지도록 공식을 다시 잡았다(유저 요청).**
계수까지 전부 `int` 로 두고 정수 연산만 쓴다. 체력·공격력·피해량·회복량에 소수점이 나오지 않으며, `DamageableUnit.currentHp` 자체도 `int` 다.

```
maxHp     = hpBase(40) + 체력 × hpPerStat(10)          → 50 ~ 1040
attack    = attackBase(2) + 공격력 × attackPerStat(2)   → 4 ~ 202 (항상 짝수)
damage    = max(minDamage(1), round(attack × 50 / (50 + 방어력)))   ← 반올림 정수 나눗셈
회복      = regenTickSeconds(10초)마다 (회복력 × regenPerStat(1)) 만큼 정수 회복
```

- **방어력 감소 곡선은 이전과 완전히 동일하다** — `50/(50+d)` 는 기존 `100/(100+2d)` 와 같은 식이다. 계수만 정수로 줄였다.
- **비율 감소를 쓰는 이유**: 감산식(`atk-def`)은 방어력≥공격력에서 완전 무적이 되고, 웨이브 배율로 적 공격력이 커지면 방어력이 무의미해짐. 비율식은 방어력 100에서도 67% 감소에 그쳐 무적이 안 나옴. 최소 피해 1 이 항상 관통.
- **정수 나눗셈을 쓴 이유**: 비율 감소는 나눗셈이라 계수를 어떻게 골라도 모든 (공격,방어) 조합에서 나누어떨어지게 만들 수 없다. "실수로 계산하고 표시만 반올림" 대신 **처음부터 반올림 정수 나눗셈**(`BalanceConfigSO.DivRound`)으로 계산해 결과를 정수로 확정한다. 결정론적이라 같은 조합이면 항상 같은 값.
- **회복을 틱으로 바꾼 이유**: 초당 소수점 회복(`0.08/s`)을 매 프레임 누적하면 체력이 정수로 안 떨어진다. 10초 간격으로 정수량을 한 번에 넣는다. 전투 중에는 틱 누적이 리셋된다.
- **배율은 전부 퍼센트(정수)** — `hpMultiplier(float 2.5)` → `hpPercent(int 250)`, 웨이브 배율 `1+0.12(w-1)` → `100+12(w-1)%`. 배율은 실효값이 아니라 **능력치에 먼저 곱한 뒤 반올림**되므로 치환 결과도 정수로 유지된다.

**재생 규칙**(유저 확정 사항): 전투(공격했거나 피해입은 상황)에서 벗어난 뒤 **5초 대기 후 재생 시작**. `BalanceConfig.outOfCombatRegenDelay` 로 조정 (이제 에셋에도 명시적으로 들어있음).

```csharp
public bool IsInCombat => Time.time - _lastCombatTime < outOfCombatRegenDelay;
```
공격을 가한 쪽도 `MarkCombatAction()`을 반드시 호출해야 전투 상태로 잡힘 (피해를 안 입어도).

## 5. 유닛 생성 구조 — 템플릿 복제 패턴

**유저 요청사항**: "하이라키에 캐릭터 객체 만든 다음 생성될 때마다 그 객체에 테이블 값 넣어서 복사하는 구조". 이후 몬스터도 동일 패턴 확장 요청.

```csharp
CharacterUnit unit = Instantiate(characterTemplate, pos, rot, parent);
unit.gameObject.SetActive(true);   // 템플릿은 비활성으로 둠
unit.Initialize(rolledStats, balance);
```

- `Instantiate`는 씬 오브젝트/프리팹 둘 다 받으므로, 템플릿을 나중에 프리팹으로 승격해도 코드 수정 불필요.
- 템플릿에 Animator·Collider·자식오브젝트(HP바 등) 붙이면 생성되는 모든 유닛이 자동으로 물려받는다.
- **클래스 계층**: `DamageableUnit`(abstract, 체력/피해/재생/전투상태/이벤트 공통 로직) ← `CharacterUnit` / `Nexus` / `MonsterUnit`. 파생클래스는 `MaxHp/DefenseStat/AttackStat/RegenStat/Faction/Kind` 4~6개 프로퍼티만 채움. 몬스터·포탑 추가 시 같은 패턴 따라가면 됨.

**⚠️ 설계 제약 하나 발견됨**: `MonsterDefinitionSO.template` 필드가 있지만 **ScriptableObject 에셋은 씬 오브젝트를 참조할 수 없음** (Unity 자체 제약). 그래서 실제로는 `MonsterSpawner.spawnTable`이 `(definition, template, count)` 3개를 한 줄에 묶는 구조로 되어 있음 — definition만으로는 부족하고 template을 스포너 쪽에서 별도로 지정해야 함. 템플릿을 프리팹으로 만들면 그때는 definition.template에 넣어도 되고, 스폰테이블의 template을 비워두면 definition.template을 자동으로 씀 (코드에 이미 폴백 처리됨).

## 6. 몬스터 & 전투 시스템

### MonsterDefinitionSO — 종류별 데이터 테이블
`Assets/_Project/Data/Units/Monster_Melee.asset` / `Monster_Ranged.asset` / `Monster_Boss.asset`

필드: 이름, tier(Normal/MidBoss/MainBoss), 4능력치, `hpPercent`(체력 보정 %, 정수), detectRange, attackRange, attacksPerSecond, moveSpeedTiles, footprintTiles.
**공격 우선순위는 tier로 자동 산출** (웨이브 기획서 p13 그대로 구현):
```csharp
TargetPriority => tier == MainBoss ? [Character,Tower,Nexus] : [Tower,Character,Nexus]
```

### UnitCombat — 자동 전투 AI (FSM)
```
Idle ─┬─ 적 인식(사거리 내) → Chase → 사거리 진입 → Attack
      ├─ advanceToObjective=true → Advance (FlowFieldService 따라 넥서스로)
      └─ 목줄(leash) 밖 → 귀환
```
- 캐릭터: `advanceToObjective=false`, leash 7타일 (넥서스 주변만 방어)
- 몬스터 3종: `advanceToObjective=true` (항상 넥서스로 전진)
- 타겟 재탐색 0.2초 간격 + 유닛별 오프셋(프레임 분산), separation(뭉침 방지) 힘, 대각 코너 관통 방지.
- **Chase/귀환 중 벽에 막히면 우회 탐색으로 넘어간다** (14절 — 각도 프로빙, 진짜 경로탐색은 아님).

### FlowFieldService — 길찾기
넥서스 목표로 BFS 1회 계산 → 몬스터는 자기 위치의 방향벡터만 읽음 (유닛 수와 무관한 비용). `MapGenerator`와 같은 오브젝트에 붙어있음. `IsCellBlocked`는 장애물 타일맵 기준(직렬화되어 씬 재실행 후에도 유효) — **2026-08-04부터 넥서스 등 구조물 점유 칸도 포함**(14절).

### UnitRegistry
살아있는 유닛 전체를 정적 리스트로 관리, `FindTarget(from, myFaction, range, priority[])`로 진영/종류/거리 기준 최근접 탐색. `DamageableUnit.OnEnable/OnDisable`에서 자동 등록/해제.

### MonsterSpawner — "한 무리를 어떻게 스폰할지"만 담당
```csharp
spawnTable: MonsterSpawnEntry[]   // (definition, template, count) 고정 표 하나
SpawnWave(int wave)               // WaveManager 가 호출. 배율 계산 후 무작위 순서로 스폰
spawnOnStart: false               // 소환 시점은 WaveManager 가 정한다. 단독 테스트용으로만 켬
```
**중요**: `waveNumber`를 바꿔도 몬스터 "구성"은 안 바뀌고 스탯 배율(체력 `100 + 12×(w-1)%`, 공격 `100 + 10×(w-1)%` — 둘 다 정수 퍼센트)만 커집니다. 즉 **"웨이브별로 다른 몬스터 조합을 테이블에 적어놓으면 파싱되는 구조"는 아직 없습니다** — `WaveDefinitionSO` 가 다음 작업.
근거리·원거리 `moveSpeedTiles`는 2.2로 통일됨(14절) — 같이 스폰돼도 도착 시점이 갈리지 않는다.

### ⚠️ 과거 버그 — 캐릭터가 몬스터를 타겟으로 인식 못 함 (해결됨, 재발 주의)
`UnitCombat.targetPriority` 의 코드 기본값이 몬스터용(`Tower→Character→Nexus`)이었고, `UnitSpawner` 는 캐릭터 AI를 `Configure()` 하지 않기 때문에 씬의 `Character_Template` 에 그 값이 그대로 직렬화돼 있었음. 캐릭터의 적은 `UnitKind.Monster` 뿐인데 우선순위 목록에 Monster 가 없어서 **캐릭터가 영원히 타겟을 못 찾고 일방적으로 맞기만** 했음.
- 조치 1: 코드 기본값을 **빈 배열**(= 종류 무시, 최근접 적)로 변경. `UnitRegistry.FindTarget` 이 빈 배열을 그렇게 처리함.
- 조치 2: 씬의 `Character_Template` 우선순위를 `[Monster]` 로 패치.
- **교훈**: `Configure()` 로 덮어쓰지 않는 유닛(캐릭터·포탑)은 템플릿의 인스펙터 값이 곧 최종값이다. 새 아군 유닛을 추가할 때 이 필드를 반드시 확인할 것.

## 8. 알아둘 것 — MCP 작업 시 주의사항 (다음 세션 참고용)

1. **`update_component`로 Sprite/서브에셋 참조 불가** — `LoadAssetAtPath(path, typeof(UnityEngine.Object))`로 텍스처 메인에셋만 로드되어 Sprite 필드는 null로 남음. **씬 YAML을 직접 텍스트 패치**(`{fileID: 21300000, guid: ..., type: 3}` = PNG의 Single 스프라이트 서브에셋) 후 `load_scene`으로 리로드하는 방식으로 우회 중. 앞으로도 이 패턴 사용. **또는(14절에서 쓴 더 안전한 방법) 참조를 바꾸는 대신 같은 guid의 원본 텍스처 파일 내용/import 설정만 바꾸면 씬을 전혀 건드릴 필요가 없다.**
2. **`update_component`가 일부 필드를 조용히 무시하는 경우 있음** (예: Camera의 `orthographicSize`, TilemapRenderer의 `m_Mode`) — 반드시 씬 YAML을 직접 grep해서 실제 적용됐는지 검증할 것. 직렬화 필드명(`m_` 접두사)과 공개 프로퍼티명이 다를 수 있음.
3. **손으로 만드는 `.asset` YAML에 빈 줄 넣지 말 것** — Unity YAML 파서가 빈 줄 이후 필드를 전부 무시함. 실제로 이 버그 때문에 바이옴 에셋의 벽 타일이 한동안 안 그려졌던 적 있음 (원인 특정 후 재작성으로 해결).
4. **씬 오브젝트 참조(Transform 등)는 MCP로 설정 불가** — 인스펙터에서 직접 드래그하거나, 같은 씬 안이면 fileID를 알아내 YAML 패치.
5. **플레이 모드 중 `save_scene` 실패** — 항상 `get_play_mode_status`로 Edit mode 확인 후 저장.
6. **패키지 버전은 레지스트리에서 Unity 6000.3 호환 버전으로 직접 확인 필요** — `latest` 태그는 상위 버전 전용일 수 있음. `com.unity.2d.pixel-perfect`는 URP 패키지에 내장되어 있으므로 별도 설치 금지(중복 컴포넌트 발생).
7. **MCP Unity 패키지의 "Claude Code" 전역 설정 버튼은 버그 있음** (`McpUtils.cs`가 프로젝트 경로 대신 패키지 경로로 조회) — 프로젝트 루트에 `.mcp.json` 직접 생성하는 방식으로 우회함 (완료됨, 재발 방지용 기록).
8. **`execute_menu_item`으로 메뉴를 실행해도 실제로 안 돌아갈 때가 있다** — 플레이 모드를 오간 직후 등 에디터 상태가 애매할 때 "성공" 응답만 오고 아무 변화가 없었던 사례 있음(21절). 맵 재생성처럼 **결과를 확인할 수 있는 값**(seed, 로그의 통계치 등)이 있는 호출은 반드시 그 값이 실제로 바뀌었는지 재확인할 것.
9. **이 진행상황 문서가 있는 `C:\Project\라스트 생츄어리\` 는 Obsidian 볼트이지 git 저장소가 아니다 — 파일시스템에 백업이 없다.** 2026-08-05, 다른 세션이 이 문서의 1~19절을 통째로 날리고 20절부터 새로 쓴 사고가 있었다(15절 참조). Obsidian 의 File Recovery 코어 플러그인은 켜져 있지만(`core-plugins.json`) 그 스냅샷은 앱 내부에 저장되고 **Obsidian MCP 도구에는 history/recovery 액션 자체가 없어 접근 불가** — 복구하려면 Obsidian 앱을 직접 열어 파일 히스토리 UI를 확인해야 한다. **이 문서를 통째로 다시 쓸 일이 있으면 덮어쓰기 전에 반드시 기존 내용을 먼저 다 읽고 병합할 것 — Write 로 밀어버리지 말 것.**

## 11. 웨이브 타이머 (`WaveManager`)

`Assets/_Project/Scripts/Wave/WaveManager.cs` · 씬의 루트 오브젝트 **WaveManager** 에 부착.

### 진행 흐름
```
게임 시작 → [Preparation] 대기시간 타이머
          → 0초 도달 시 맵 가장자리 스폰 게이트에서 몬스터 소환, 넥서스로 진군
          → [Marching] 웨이브 타이머는 아직 정지 상태
          → 몬스터 ↔ 아군 첫 공격 발생 → [Battle] 웨이브 타이머 시작
          → 0초 도달 시 웨이브 번호 +1 → 다시 [Preparation]
```
진군 구간에서 타이머를 세지 않기 때문에 맵이 커도 전투 시간이 깎이지 않는다(섹션 3 참조).

### 인스펙터에서 조정하는 값
| 필드 | 기본값 | 의미 |
|---|---:|---|
| `preparationSeconds` | 30 | 대기(정비)시간. 게임 시작 시에도 이 타이머가 먼저 돈다 |
| `battleSeconds` | 120 | 첫 전투 시점부터 재는 웨이브 지속 시간 |
| `startWave` | 1 | 시작 웨이브 번호 |
| `autoStart` | ✔ | 끄면 `StartGame()` 을 직접 호출해야 시작 |
| `logPhaseChanges` | ✔ | 단계 전환을 콘솔에 남김 (UI 전까지 유일한 확인 수단) |

우클릭 컨텍스트 메뉴 **"현재 단계 건너뛰기"** 로 타이머를 즉시 넘겨 밸런싱 테스트 가능.

### 전투 개시 감지 방식
`DamageableUnit.OnAnyAttack` 정적 이벤트(공격자, 대상). `TakeDamageFrom(DamageableUnit)` 안에서 한 번만 발생하므로 호출 지점이 흩어지지 않는다. `WaveManager` 는 Marching 단계에서 몬스터↔Angel 진영 공격이 처음 잡히는 순간 Battle 로 전환한다. 정적 이벤트라 `RuntimeInitializeOnLoadMethod` 로 구독을 초기화한다(도메인 리로드 off 대비).

### 외부에서 읽을 수 있는 값 (UI 붙일 때)
`Phase` / `WaveNumber` / `PhaseRemaining` / `PhaseDuration` 프로퍼티, `OnPhaseChanged` / `OnWaveSpawned` / `OnWaveEnded` 이벤트.

### ⚠️ 함정 — `Run In Background` 가 꺼져 있으면 타이머가 안 흐른다
`ProjectSettings > Player > Run In Background` 가 **0** 이면 에디터 창이 포커스를 잃는 순간 게임 루프가 멈춘다. 대기시간 30초 / 웨이브 120초처럼 긴 타이머를 쓰는 이 프로젝트에서는 "플레이를 눌렀는데 아무 일도 안 일어난다"로 보인다. 실제로 MCP로 검증하다가 `PhaseRemaining` 이 3초짜리 타이머에서 몇 분째 2.96 으로 멈춰 있는 걸 확인함.
`ProjectSettings.asset` 을 텍스트로 고쳐도 **에디터가 메모리에 캐시하고 있어 재시작 전까지 반영되지 않는다** — 에디터 UI에서 직접 켜거나 Unity 재시작 필요.

### ⚠️ 사망한 유닛이 씬에 남던 문제 (해결됨)
`CharacterUnit.OnDeath` / `Nexus.OnDeath` 가 로그만 남기고 오브젝트를 지우지 않아서, 캐릭터가 전멸하고 넥서스까지 파괴된 뒤에도 시체가 그대로 보였다. 몬스터는 타겟이 사라지면 `Advance` 로 돌아가 플로우 필드 목표(맵 중앙 = 넥서스 자리)에 도달해 그 자리에서 멈춘다. 결과적으로 **"몬스터랑 캐릭터가 다 넥서스에 붙어서 아무 일도 안 일어나는"** 화면이 된다 — 사실은 전투가 이미 끝난 것.
- `CharacterUnit.OnDeath` → `Destroy(gameObject)` (몬스터와 동일하게)
- `DamageableUnit.OnAnyDied` 정적 이벤트 추가 → `WaveManager` 가 넥서스 파괴를 잡아 `WavePhase.Defeat` 로 전환하고 타이머를 멈춘다 (`OnDefeat` 이벤트 제공)
- 넥서스 오브젝트 자체는 남긴다(폐허). 패배 연출/재시작은 미구현.

### 아직 없는 것
웨이브별 몬스터 구성 변화(배율만 커짐), 사이클/보스 웨이브 규칙, 정비시간 초과 광폭화, 남은 몬스터 정리 규칙(웨이브가 끝나도 살아있는 몬스터는 그대로 남는다).

## 12. 전장의 안개 & 캐릭터 자율 이동

### FogOfWarService (`MapGenerator` 오브젝트에 부착)
맵 한 칸 = 텍스처 한 픽셀인 `Texture2D`(320x320, Point 필터)를 스프라이트로 만들어 맵 전체를 덮는다. 타일맵을 하나 더 쓰지 않으므로 맵이 커져도 갱신 비용이 일정하다. `FogOverlay` 자식 오브젝트는 **런타임에 자동 생성**되므로 씬에 미리 만들 필요 없다.

칸 상태 3단계:

| 상태 | 색 | 의미 |
|---|---|---|
| 미탐사 | `unexploredColor` (불투명) | 한 번도 못 본 곳 |
| 탐사됨 | `exploredColor` (알파 0.6) | 봤지만 지금은 시야 밖 |
| 시야 내 | 완전 투명 | 지금 누군가 보고 있음 |

인스펙터 조정: 두 색상, `sortingLayer`(Overhead) / `sortingOrder`(100), `refreshInterval`(0.1초), `enableFog`(끄면 안개 자체가 안 생김 — 디버깅용).
조회 API: `IsExplored(cell)` / `IsVisible(cell)` / `ExploredCount` / `ExploredPercent` / `TryFindUnexploredTarget(...)`.
**맵을 다시 생성하면 `Build()` 를 호출해야 크기가 맞는다** (현재 자동 연동 없음).

### VisionSource — 시야를 제공하는 쪽
시야는 **"한 변 몇 타일"**로 지정한다 (`visionTiles`). 반경은 그 절반.
- `Character_Template` → **5** (5x5 칸, 반경 2.5) — 유저가 에디터에서 조정하는 값
- `Nexus_Template` → **10** (10x10 칸, 반경 5)

템플릿에 붙어 있으므로 복제되는 모든 유닛이 자동으로 물려받는다. 포탑 등 새 유닛에 시야를 주려면 이 컴포넌트만 붙이면 된다.

### CharacterBehavior — 캐릭터 자율 이동
이동 코드를 새로 짜지 않고, **`UnitCombat` 의 귀환 지점(home)을 옮기는 것으로 이동 명령을 대신한다.** `UnitCombat` 은 타겟이 없으면 귀환 지점으로 걸어가기 때문에, 목적지만 갈아끼우면 된다. 교전 중(`UnitCombat.Target != null`)에는 목적지를 건드리지 않는다.

| 상황 | 행동 |
|---|---|
| `WavePhase.Preparation` | **정찰** — 미탐사 칸을 목표로 나가 전장을 밝힌다 |
| 그 외 (진군/전투/패배) | **방어** — 넥서스 반경 안 임의 지점을 순찰한다 |

인스펙터 조정값: `scoutMinDistance`(14) / `scoutSearchRadius`(60) / `scoutLeash`(6) / `scoutTimeout`(15) / `guardRadius`(8) / `guardLeash`(7) / `guardRepositionDelay`(2.5~6초) / `arriveDistance`(1.2).

**`scoutMinDistance` 가 왜 필요한가**: 가장 가까운 미탐사 칸을 고르면 자기 시야 경계(반경 2.5) 바로 바깥이 목표가 되어, 3타일 가고 다시 고르기를 반복하며 제자리에서 맴돈다. 최소 거리를 줘야 한 방향으로 쭉 나갔다 오는 정찰다운 움직임이 나온다. 같은 링의 후보 중에서는 무작위로 골라 캐릭터 3명이 한 곳으로 몰리지 않게 했다(캐릭터마다 `GetInstanceID()` 기반 별도 난수열).

### ⚠️ 몬스터 템플릿이 활성 상태였던 문제 (해결됨)
`Templates` 라는 이름의 **루트 오브젝트가 두 개** 있고, 몬스터 3종이 든 쪽은 활성이었다. 즉 게임 시작부터 몬스터 3마리가 살아 움직이며 넥서스로 진군하고 `UnitRegistry` 에도 등록돼 있었다. 몬스터 템플릿 3개를 각각 비활성으로 바꾸고, 이후 루트를 하나로 합쳐 `Templates/Monster_Templates/` 하위로 정리했다(현재 씬 구조 1절 참조).

### ⚠️ MCP 로 비활성 오브젝트는 조회/수정이 안 된다 — `objectPath` 대신 `instanceId` 를 쓸 것
`update_component` / `update_gameobject` / `get_gameobject` 의 **경로(`objectPath`) 조회는 비활성 오브젝트를 못 찾는다**(`GameObject with path '...' not found`). 템플릿은 전부 비활성이므로 경로로는 손을 댈 수 없다.
**해결: `get_scenes_hierarchy` 로 받은 `instanceId` 를 `update_component` 에 넘기면 비활성 오브젝트도 수정된다.** 단 이 `instanceId` 는 **그 응답 안에서만 유효한 임시 값**이다 — 다른 호출에서 받은 instanceId 를 재사용하면 "not found" 가 난다. 패턴: `get_scenes_hierarchy` 호출 → 그 응답에서 바로 instanceId 를 읽어 같은 턴에 `update_component` 호출.

### ⚠️ `load_scene` 의 "성공" 응답이 실제 리로드를 보장하지 않는다 (씬 YAML 직접 패치 워크플로우의 함정)
씬 YAML을 직접 텍스트 패치한 뒤 `load_scene` 으로 반영하는 패턴(8절)은 **새 GameObject/컴포넌트 추가**에는 잘 통했지만, **이미 있는 컴포넌트의 필드 값만 바꾸는 패치**에서는 실패한 적이 있다. `load_scene` 이 "성공"을 반환했는데도 실제 에디터의 라이브 씬 객체는 갱신되지 않아, 그 뒤에 `save_scene` 을 부르니 (반영 안 된) 옛 메모리 상태로 디스크 파일을 덮어써 방금 패치한 값이 그대로 날아간 사례가 있었다(`UnitCombat.respectFogOfWar` 를 1로 패치 → load_scene "성공" → 한참 뒤 save_scene → 다시 grep 해보니 0으로 되돌아가 있었음).
**대응**: YAML 패치 후 `load_scene` 을 불렀다면, **곧바로 grep 등으로 재검증하지 말고 `save_scene` 을 부르기 전에 `get_gameobject`/`update_component` 로 라이브 객체 값을 확인·재적용하는 편이 안전하다.** 기존 컴포넌트의 필드 값 변경은 애초에 YAML 패치보다 `update_component`(instanceId 사용, 위 항목 참조)가 더 믿을 만하다 — YAML 직접 패치는 **새 오브젝트/컴포넌트를 추가**할 때만 쓸 것.

## 13. 벽 충돌 & 전투 시야에 안개 반영

### ⚠️ 문제 — 캐릭터·몬스터가 벽을 그냥 뚫고 지나감 (해결됨)
유닛(`Character_Template`/몬스터 템플릿)에는 **Collider2D 가 없다.** `UnitCombat.Step()` 은 `transform.position +=` 로 직접 좌표를 옮기기만 해서, 물리 충돌이 걸릴 여지가 원래 없었다.
`Advance` 상태(몬스터가 넥서스로 전진)는 `FlowFieldService` 가 벽을 피해가는 방향만 골라주므로 우연히 문제가 안 됐지만, **`Chase`(적 추격·목줄 귀환)는 목표까지 직선 이동**이라 사거리 안의 적이 벽 반대편에 있으면 벽을 그대로 뚫고 다가갔다.

- [MapGenerator.cs](Assets/_Project/Scripts/Map/MapGenerator.cs) 에 `WorldToCell(Vector3)` 공개 메서드 추가 (기존 `FlowFieldService` 의 비공개 헬퍼와 동일 로직, 재사용 목적).
- [UnitCombat.cs](Assets/_Project/Scripts/Combat/UnitCombat.cs) `Step()` → `MoveWithCollision()` 신설. 이동 전 목적지 칸이 `MapGenerator.IsCellBlocked` 로 막혀 있으면, x축만/y축만 순서로 미끄러뜨려본다(고전적인 축 분리 슬라이딩). 둘 다 막히면 그 프레임은 정지. **(14절에서 이 뒤에 각도 프로빙 우회 탐색이 추가됨)**
- 물리 콜라이더를 추가하지 않고 **타일맵 기준 셀 판정**으로 처리했다 — `FlowFieldService`/`MapGenerator.IsCellPlaceable` 과 같은 방식이라 프로젝트 전체가 일관된다.
- 큰 유닛(보스, footprint 3타일)은 셀 하나만 검사하므로 코너에서 살짝 파고들 수 있음 — 지금까지의 배치 판정(`TryFindPlaceableNear` 등)도 같은 수준이라 일단 맞춤.

### 안개가 순수 시각효과였던 것 → 캐릭터 전투 시야에 반영 (몬스터는 예외)
지난 세션에서 "안개가 전투에 영향 없음"을 다음 단계로 남겨뒀던 것을 처리했다. 유저 요청대로 **캐릭터는 안개에 가려진 적을 타겟으로 인식하지 않고, 몬스터는 지도 전체가 항상 밝혀진 것처럼 공격**하게 갈랐다.

- [UnitRegistry.cs](Assets/_Project/Scripts/Combat/UnitRegistry.cs) `FindTarget`/`NearestOfKinds` 에 선택적 `filter` 매개변수 추가. 기존 호출부(몬스터)는 그대로 두면 `null` 이라 동작이 안 바뀐다.

## 14. 넥서스 충돌 판정 + 이동 우회 탐색 + 몬스터 이동속도 통일 + 캐릭터 스프라이트 2등신(2:1) 임포트 (2026-08-04)

- `FlowFieldService`는 `IsCellBlocked`를 그대로 재사용하므로 코드 변경 없이 넥서스 칸을 자동으로 피해간다. 목표 셀(넥서스 중심) 자체가 "막힘" 처리돼도 BFS 시작점은 무조건 거리 0으로 강제 설정되므로 goal 도달 판정은 깨지지 않는다(코드 검토로 확인).

- ⚠️ **런타임에서만 검증 가능** — 등록은 `Start()`에서 일어나므로 플레이 모드에서만 동작 확인 가능. 이 세션에서는 Play 모드 테스트를 하지 않았다(상단 "작업 방식" 참조) — **다음에 에디터에서 직접 확인할 것.**

## 20. 벽 이미지 자체를 수정해 입체감 부여 (2026-08-04 6차)

19절에서 방향별 타일을 제대로 골라 깔았는데도 **"그냥 이미지 자체가 입체감이 없다"** 는 피드백. 맞는 지적이었다 — 배치 로직이 아니라 **그림의 명암 구조** 문제였다. 이미지를 직접 수정했다.

### 진단 (픽셀 단위로 측정)

**① South 타일의 립이 기하학적으로 반대에 있었다.** 작가가 "어두운 측면 + 밝은 립" 규칙을 네 방향에 기계적으로 같이 적용했는데, 남쪽만 방향이 뒤집힌다.

| 방향 | 어두운 측면 | 밝은 립 | 판정 |
|---|---|---|---|
| North | row 0-3 | row 4 (안쪽) | ✅ |
| West | col 0-2 | col 3 (안쪽) | ✅ |
| East | col 17-19 | col 16 (안쪽) | ✅ |
| **South** | row 14-18 | **row 19 (바깥쪽)** | ❌ |

South 는 카메라를 향한 정면이라 립이 **윗면과 만나는 위쪽**(row 13-14)에 있어야 한다. 맨 아래(row19)에 lum 115 짜리 밝은 선이 있어서 **밑동이 빛나고** 벽이 서 있는 느낌이 죽었다. 3/4 뷰에서 벽 밑동은 접지 그림자로 가장 어두워야 하는 자리다.

**② 앞면이 5px(타일의 25%)뿐이라** 수직 벽으로 읽히지 않았다.

**③ `Wall_Inner` 32개 변형의 평균 밝기 편차가 32단계(53~85).** 칸마다 랜덤으로 깔리니 벽 덩어리가 **체커보드처럼 얼룩져서** 하나의 면으로 안 보였다. (참고: 바닥 타일 평균 밝기 61)

### 고친 방식 — "평탄화 후 재음영"

[Tools/wall_depth_pass.py](Tools/wall_depth_pass.py) (Python + Pillow, Unity 밖에서 실행)

1. **평탄화** — 원본의 어두운 측면 밴드와 밝은 립 선을 전부 윗면 목표 밝기(86)로 되돌려 균일한 평면을 만든다. 곱셈이라 픽셀 텍스처는 그대로 남는다.
2. **재음영** — 노출된 최근접 변 기준으로 역할(top/lip/face/shadow)을 다시 계산해 칠한다. 최근접 변 판정이라 **모서리 타일의 립이 자연스럽게 45도로 만난다.**

적용 결과 (South 타일 행별 밝기):
```
전:  61 61 60 59 57 56 60 71 69 66 64 62 62 63 | 31 40 42 44 46 | 115
후:  82 82 81 80 77 76 81 96 |132| 64 59 54 51 48 44 41 38 34 31 | 20
     └─── 윗면(균일) ───┘  립   └── 앞면 10px 하강 ──┘        접지
```

- **앞면을 10px(타일의 50%)로 키우고** 위→아래로 어두워지는 그라데이션을 줬다. 벽 높이가 느껴진다.
- **립은 남쪽에만 준다.** 네 변에 다 주면 덩어리가 네온 테두리를 두른 평판처럼 보인다(중간에 실제로 그렇게 실패했다). 북/서/동은 윗면이 끝나는 얇은 어두운 리브만 남긴다.
- `Wall_Inner` 32개 변형 밝기를 **편차 32 → 1** 로 정규화해 얼룩을 없앴다. 아주 약한 좌상단 라이팅만 남김.

### ⚠️ 구현 중 밟은 함정 두 개 (같은 작업 다시 할 때 주의)

## 21. 벽을 2칸 높이로 새로 그려 예전 수준의 입체감 복원 (2026-08-05)

20절에서 명암은 고쳤지만 유저 피드백은 "그래도 저번(16x32 벽)만큼 입체감이 안 산다"였다. 맞는 말이었다 — **20x20 한 칸 안에서는 정면이 최대 10~20px** 이라 구조적으로 한계가 있었다. 20절 끝에 남겨둔 대로, 이번엔 실제로 **아트를 2칸 높이(20x40)로 새로 그렸다.**

### 원리 — 예전 프로젝트가 이미 썼던 방식 그대로
1절에 적혀 있던 "벽 3종(16x32, 3/4뷰: 윗면+정면+접지그림자), Individual 모드 + TopLeft 정렬"이 바로 이 기법이다. 스프라이트를 셀보다 2배 높게 만들고 피벗을 좌상단(TopLeft)에 두면, 타일맵이 그 칸에 놓을 때 이미지 위쪽이 칸 상단에 맞춰지고 나머지 절반이 **아래(남쪽, 카메라 쪽)로 늘어져 다음 칸 위에 겹쳐** 그려진다. 그 늘어진 절반이 벽의 "정면"이 되어, 벽이 실제로 바닥에서 솟아오른 것처럼 보인다.

### 무엇을 했나 — [Tools/wall_extrude_pass.py](Tools/wall_extrude_pass.py) (신규)
`_ArtBackup/`의 **원본**(20절 이전, 밴드가 남아있는 순수 원본)을 읽어 `Wall_Outer_20px.png` 를 20x20 → **20x40** 으로 다시 그린다. 한 타일 구성(위→아래):

```
rows  0-19  지붕(top)   — 줄 단위로 평탄화한 재질 (20절 기법 재사용, 밴드 제거)
row     20  립(lip)     — 지붕과 만나는 밝은 하이라이트, 방향별로 밝기 다름
rows 21-37  정면(face)  — 평탄화된 재질을 세로로 이어붙여 재사용, 위→아래 어두워짐
rows 38-39  접지 그림자  — 거의 검정
```

방향별 톤(빛은 좌상단에서 온다고 가정): **남쪽이 립 대비가 가장 크고**(가장 눈에 띄는 정면), 서쪽이 가장 밝음(빛을 받는 면), 북/동쪽은 상대적으로 어둡다. 모서리는 두 방향의 값을 평균낸다.

### ⚠️ 1차 시도 실패 — 20절과 같은 실수를 그대로 반복했다
처음엔 "지붕"을 만들 때 원본 20x20 전체를 **평균 하나**로만 정규화했다. 결과: 원본에 이미 있던 밝은 립/노치 밴드가 비율을 유지한 채 그대로 남아 지붕에 얼룩덜룩한 줄이 다시 나타났다(North 타일 row4 에 131 짜리 스파이크가 그대로 있었음). **20절에서 이미 겪은 정확히 같은 실수**(밴드를 "영역 평균"으로 지우려 하면 밴드 내부 기울기가 남는다)를 새 스크립트에서 재현한 것 — 20절의 줄 단위(`SRC_BAND`, 방향별 최근접 변까지의 거리 기준) 정규화 로직을 그대로 재사용하고서야 지붕이 균일해졌다(측정: 밴드 스파이크 131/108 → 균일 80~98대).

### 핵심 안전장치 — Tile 에셋 32개를 손대지 않았다
`.meta` 안 각 스프라이트의 `rect.height`(20→40)·`rect.y`(재계산)·`alignment`(0→1, TopLeft)·`pivot`({0.5,0.5}→{0,1})만 바꾸고, **`internalID`/`spriteID`/이름은 그대로 뒀다.** Tile 에셋은 `{fileID: internalID, guid: PNG의 guid}` 로 스프라이트를 참조하는데 둘 다 안 바뀌었으므로, **32개 `Wall_Outer_*.asset` 파일을 단 하나도 새로 만들거나 열지 않고 그대로 유효했다.** (South_01 검증: 에셋의 `m_Sprite fileID: 5238423401504020478` = meta의 `internalID: 5238423401504020478`, 일치.)

### 후속 (같은 날) — 빗금 밴드 제거 + 피벗 버그 수정

유저 지적: **"아우터 라인들 아래쪽에 있는 빨간색 빗금 영역 때문에 이미지가 이질적이다."** 원인 두 개를 찾아 고쳤다.

**① 빗금의 정체 — `Wall_Outer` 원본 밴드에 세로 말뚝 패턴이 있었다**
원본 South 타일을 픽셀로 찍어보니 rows 14-18 이 세로 빗금이었다:
```
 14 :    : :  : :  :
 15 :....:.:..:.:..:....
 16 :....:.:..:.:..:....   <- 이 빗금
 17 :....:.:..:.:..:....
 18 :....:.:..:.:..:....
```
21절 스크립트는 이 원본을 재질로 쓰면서 `src_y = fy % TILE` 로 세로 반복시켰다 → **지붕과 정면에 빗금이 두 번 반복돼** 나왔다. 밝기만 평탄화해봐야(20·21절 기법) 줄별 평균만 맞춰지고 **한 줄 안의 가로 방향 변화(빗금)는 그대로 남는다** — 평탄화로는 절대 못 지우는 종류의 패턴이었다.

**해결: 재질을 `Wall_Inner` 에서 가져온다.** `Wall_Inner_Fill` 은 빗금 없는 유기적 텍스처다(대조 확인함). 이제 `Wall_Outer` 자신의 픽셀은 **전혀 쓰지 않고**, Inner 변형 32개를 방향×변형에 하나씩 배정해 지붕/정면 재질로 쓴다. 부수 이점으로 내부 채움 칸과 재질이 같아져 **벽 덩어리가 하나의 표면으로 읽힌다.** 방향 정보(리브·립·그림자)는 코드가 직접 그린다:
```
rows  0-19  지붕  — 깨끗한 재질 + 노출된 N/W/E 변에 2px 어두운 리브
row     20  립    — 지붕/정면 경계 하이라이트 (유저가 말한 "아우터 라인")
rows 21-37  정면  — 같은 재질 세로 반복 + 위(0.76)→아래(0.40) 그라데이션
rows 38-39  접지 그림자 (0.18)
```

**② 피벗 버그 — 21절에서 내가 잘못 넣었다 (벽이 반 칸 밀리는 상태였음)**
21절에 `alignment: 1`(TopLeft) + `pivot {0, 1}` 을 넣었는데, `Tilemap.tileAnchor` 가 `(0.5, 0.5)` 라 **스프라이트 피벗이 칸 중심에 놓인다.** TopLeft 피벗이면 스프라이트 좌상단이 칸 중심에 오므로 벽이 반 칸 오른쪽으로 밀리고 2칸 아래로 늘어진다. 계산해서 바로잡았다:
```
칸 (x,y) = 월드 [x,x+1]x[y,y+1],  스프라이트 20x40 @PPU20 = 1x2 유닛
원하는 범위: [x,x+1]x[y-1,y+1]   (지붕=자기 칸, 정면=남쪽으로 늘어짐)
bottom-left=(x,y-1),  피벗=bottom-left+(px*1, py*2)=(x+0.5, y+0.5)
  -> px=0.5,  2*py=1.5  ->  py=0.75
```
→ **`alignment: 9`(Custom) + `pivot {x: 0.5, y: 0.75}`**. 21절 상태로는 실제 화면에서 벽이 어긋나 보였을 것이다(유저가 플레이해봤지만 빗금이 더 눈에 띄어 이 문제는 언급 안 했을 수 있다).

**멱등성도 고쳤다.** 21절 meta 재작성은 행 인덱스를 `y // 20`(하드코딩)으로 구해서, 두 번 실행하면 y 가 0/80/160/240 으로 튀어 깨졌다. 이제 **meta 에 적힌 현재 height 로 나눠** 계산하므로 몇 번을 실행해도 같은 결과다(연속 2회 실행으로 검증).

**확인된 것**
- 새 South 타일 픽셀 덤프: 지붕 유기적 텍스처, row20 균일한 립(`++++`), 정면 매끄러운 하강, 38-39 그림자. **빗금 없음.**
- 32개 스프라이트 전부 `pivot (0.5, 0.75)` / `alignment 9` / `height 40`, `internalID` 유지(South_01: 에셋 `m_Sprite fileID 5238423401504020478` = meta `internalID` 일치) → **Tile 에셋 32개 무손상.**

- **맵 재생성 불필요** — 타일 에셋을 안 건드렸으므로 기존 맵 데이터가 그대로 새 아트로 렌더된다.
- ⚠️ 작업 중 `LastSanctuary > 맵 > 새 시드로 맵 생성` 메뉴가 "성공"을 반환하고도 실제로 안 돌아간 적이 있다(시드·로그 변화 없음). 유저가 플레이 모드를 오간 직후여서 에디터 상태 문제로 보인다. **이 메뉴를 쓴 뒤에는 `MapGenConfig.seed` 가 실제로 바뀌었는지 확인할 것.**

## 22. 중립 몬스터 — 서식 · 정찰 중 사냥 · 에너지 획득 (2026-08-05)

유저 요청: `데이터 테이블/임시용 중립 몬스터.xlsx`(neutrality_mon 시트)를 확인해 중립 몬스터를 구현할 것. 이 테이블의 `spawn_range` 칸은 **"넥서스 기준 n×n 타일 구역부터 나타날 수 있다"는 하한 조건**이라는 유저 설명을 받음 — 상한은 없다(더 멀리서도 계속 나타남). 빈 칸(에너지·능력치)은 밸런스를 봐서 임의로 채우고, 생성 주기도 테이블에 없어 임의로 설계하라는 지시. 추가로 **캐릭터 AI에 "탐색 중 중립 몬스터 조우 시 사냥 → 에너지 획득" 로직**을 붙여달라는 요청.

원래 채워져 있던 값은 `mon_id`/`mon_name`/`spawn_range`/`atk_take` 뿐이었다. **`atk_take`(선공 여부)**: 1001은 0(무해한 사냥감, 절대 먼저 공격 안 함), 1002·1003은 1(발견하면 먼저 공격).

⚠️ **엑셀 파일이 이번 세션 내내 Excel에서 열려 있는 상태(`~$임시용 중립 몬스터.xlsx` 잠금 파일 확인됨)라 파일 자체에 값을 다시 써넣지 못했다.** 아래 "채운 값"이 실제 게임에 반영된 최종 수치이므로, 원본 xlsx 를 갱신하고 싶으면 Excel을 닫은 뒤 아래 표대로 채워 넣을 것.

### 빈 칸을 채운 값 — 근거와 함께

기존 웨이브 몬스터 스탯(6절 — 근거리 7/5/2/0 → HP110·타격12, 원거리 6/4/1/0 → HP100·타격10)을 기준으로 **1~100 raw 스탯 척도를 그대로 재사용**해서 `BalanceConfigSO` 치환 공식을 통일했다(atk/hp/def/hp_regen 칸을 새 시스템의 raw 스탯으로 취급). `spawn_range`가 클수록(넥서스에서 멀수록) 더 강하고 보상도 크게 잡았다.

| mon_id | atk | hp | def | hp_regen | min_energy | max_energy | → 실효 HP | 실효 타격 | 피해감소 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1001 | 0 | 3 | 0 | 0 | 5 | 10 | 70 | (전투 안 함) | 0% |
| 1002 | 4 | 6 | 1 | 1 | 15 | 25 | 100 | 10 | 2% |
| 1003 | 8 | 10 | 3 | 2 | 30 | 50 | 140 | 18 | 6% |

- **1001(무해)**: `atk_take=0`이므로 `UnitCombat` 자체를 스폰 시점에 꺼버린다 — 표의 `atk=0`은 그냥 데이터일 뿐, 실제로는 절대 공격하지 않는 "사냥감" 전용 개체다.
- **1002·1003(선공)**: 웨이브 1의 원거리·근거리 몬스터와 비슷한 수준 ~ 조금 더 강한 수준으로 잡았다 — 정찰 중 마주치는 위협이 웨이브 몹과 동떨어지지 않게.
- **에너지 보상**: 멀리 나갈수록(강할수록) 크게 — 1001은 캐릭터 생성 직후에도 안전하게 잡을 수 있는 "튜토리얼 사냥감", 1003은 원정 보상.

### 생성 주기 — 테이블에 없어 임의로 설계함

기획 테이블에 스폰 주기 항목 자체가 없었다. 웨이브 몬스터(`MonsterSpawner`)는 웨이브 타이머가 트리거하는 "한 무리 생성" 방식이라 그대로 못 쓴다 — 중립 몬스터는 웨이브와 무관하게 **항상 맵에 서식**해야 하므로 새 컴포넌트 [NeutralMonsterSpawner.cs](Assets/_Project/Scripts/Units/NeutralMonsterSpawner.cs)를 만들었다:
- 게임 시작 시 정의별 **개체수 상한**(1001: 15마리 / 1002: 8마리 / 1003: 4마리 — 강할수록 희소하게)까지 즉시 채운다.
- 이후 **20초(`restockInterval`)마다** 개체수를 확인해, 상한보다 부족하면 종류당 최대 2마리(`maxSpawnPerRestock`)씩 보충한다. 한 번에 상한까지 다 채우면 리스폰이 몰려서 티가 나므로 나눠서 채우는 방식을 택했다.
- 상한·주기 모두 인스펙터에서 조정 가능한 임의값 — 실제 플레이해보고 밸런싱 필요.

### 등장 범위 판정 — "n×n 타일부터"를 코드로

넥서스는 항상 셀 (0,0)에 있다(`MapGenerator.CenterCell`). `spawn_range`(n)의 절반을 **체비셰프 거리**(정사각 구역의 경계까지 거리, `max(|dx|,|dy|)`)로 써서 "n×n 구역 밖"을 판정한다 — `NeutralMonsterDefinitionSO.MinDistanceFromNexus`. 하한만 있고 상한이 없으므로, 먼 곳에서는 세 종류가 전부 겹쳐서 나타날 수 있다(예: 160타일 지점 — 세 조건 100/200/300의 절반인 50/100/150을 전부 만족하지는 않지만, 150 이상인 지점에서는 세 종류 다 스폰 후보가 된다). 맵이 320×320(6절)이라 세 등장범위(50/100/150 타일 반경) 전부 맵 안에 들어간다.

### 구조 — 새 진영 `Faction.Neutral`

기존 전투 AI(`UnitCombat`)는 `myFaction.Opposite()`로 적을 찾는다. 새 진영을 넣으면서 **기존 Angel↔Cancer 대칭은 절대 안 건드리는 것**이 제일 중요했다:
- [Faction.cs](Assets/_Project/Scripts/Combat/Faction.cs) — `Faction.Neutral` 추가. `Opposite()`는 `Neutral → Angel`만 새로 얹었다(선공형 중립 몬스터가 캐릭터를 적으로 인식하게). `Angel → Cancer`, `Cancer → Angel`은 그대로.
- 이 대칭 때문에 **캐릭터 쪽 `UnitCombat`은 여전히 중립 몬스터를 자동으로 적대시하지 않는다** (`Angel.Opposite() == Cancer`, 안 바뀜) — 아무 데서나 캐릭터가 야생동물을 학살하고 다니는 걸 막는다. "정찰 중에만 사냥한다"는 요청과도 맞아떨어진다.
- 대신 [UnitCombat.cs](Assets/_Project/Scripts/Combat/UnitCombat.cs)에 **`SetHuntTarget`/`ClearHuntTarget`/`IsHunting`** 훅을 추가했다 — 평소 진영 판정을 건너뛰고 "이 상대를 지금 공격하라"고 강제하는 오버라이드 경로. `AcquireTargetIfNeeded()` 맨 앞에서 우선 처리하고, 귀환 지점(`leashRange`) 밖으로 벗어나면 자동으로 포기한다.
- [CharacterBehavior.cs](Assets/_Project/Scripts/Units/CharacterBehavior.cs) — **정찰(Scout) 중에만** 주변(`huntDetectRange`, 기본 10타일) 중립 몬스터를 찾아 `SetHuntTarget`을 건다. 이미 있던 "교전 중이면 목적지 안 건드림" 가드가 사냥 중에도 그대로 작동해서 별도 이동 코드가 필요 없었다.
- 선공형(1002·1003)은 `UnitCombat`을 켠 채로 스폰돼 스스로 캐릭터를 찾아 먼저 공격한다(`Faction.Neutral.Opposite() == Angel`). 비선공형(1001)은 스폰 시 `UnitCombat.enabled = false`로 꺼서 절대 공격하지 않는 사냥감이 된다.
- [NeutralMonsterUnit.cs](Assets/_Project/Scripts/Units/NeutralMonsterUnit.cs) — `DamageableUnit` 상속, `Faction.Neutral` / `Kind.Monster`. 웨이브 배율을 안 받는다(항상 서식하므로).
- [ResourceManager.cs](Assets/_Project/Scripts/Resource/ResourceManager.cs) — `HandleDeath`에 중립 몬스터 처치 분기 추가. `NeutralMonsterUnit.RollEnergyReward()`(정의 테이블의 min~max_energy 범위)를 무작위로 지급. 기존 웨이브 몬스터 처치 보상(고정 10)과는 별도 경로.

### 아직 확인 못 한 것 (유저가 볼 것)

- **플레이 모드 검증 전혀 안 함** — 상단 "작업 방식" 원칙대로 MCP에서 플레이 모드 진입/타이머 대기를 하지 않았다. 다음에 에디터에서 직접 확인할 것: 스폰이 실제로 등장범위 밖에서만 일어나는지, 정찰 중 캐릭터가 정말 사냥하러 가는지, 에너지가 정상 지급되는지, 선공 개체가 실제로 캐릭터를 먼저 공격하는지.
- **스프라이트 미할당** — 3개 템플릿 모두 흰 사각형으로 보일 것이다. 에디터에서 원하는 아트를 SpriteRenderer에 직접 끌어다 놓을 것.
- **엑셀 원본 미갱신** — 파일이 열려 있어서 위 "채운 값" 표를 xlsx 자체에는 못 썼다. 닫은 뒤 반영 원하면 알려줄 것.
- **개체수 상한/리스폰 주기는 완전히 임의값**(15/8/4마리, 20초마다 종류당 최대 2마리) — 테이블에 근거가 없었으므로 밸런싱 필요.
- 중립 몬스터끼리는 서로 공격하지 않는다(같은 Neutral 진영끼리는 Opposite 대상이 아님) — 의도한 동작.
- 선공형 중립 몬스터가 웨이브 몬스터(Cancer)를 적대시하지도, 웨이브 몬스터가 중립 몬스터를 적대시하지도 않는다 — `Cancer.Opposite() == Angel`, `Neutral.Opposite() == Angel`이라 서로는 안 건드림. 순수하게 "캐릭터 대 중립"·"캐릭터 대 웨이브"만 존재.

### 후속 (같은 날) — 엑셀에 채운 값 반영 + 유저가 바꾼 spawn_range 동기화

엑셀 파일이 Excel에서 닫혀 잠금(`~$임시용 중립 몬스터.xlsx`)이 풀린 것을 확인하고, 위 "빈 칸을 채운 값" 표(1001: 5~10 / 1002: 15~25 / 1003: 30~50 에너지, atk/hp/def/hp_regen 동일)를 **`데이터 테이블/임시용 중립 몬스터.xlsx`(neutrality_mon 시트) 원본 파일에 직접 써넣었다** — 이제 게임에 반영된 수치와 엑셀 파일의 내용이 일치하며, 유저가 엑셀을 열어 직접 확인/재조정할 수 있다.

그 사이 유저가 `spawn_range`(몬스터 등장 범위) 값을 직접 고친 것을 재확인 시 발견했다:
| mon_id | 이전 spawn_range | **변경된 spawn_range** |
|---:|---:|---:|
| 1001 | 100 | **1** |
| 1002 | 200 | **100** |
| 1003 | 300 | **200** |

`spawn_range=1`은 사실상 넥서스 바로 옆(반경 0.5타일)부터도 나타날 수 있다는 뜻 — 1001(무해한 사냥감)이 거의 맵 전역에 나타나도록 더 완화된 것이다. 순서(1 < 100 < 200)는 그대로 유지되므로 "멀수록 강함" 밸런스 논리(1001 무해 → 1002/1003 갈수록 강함)는 안 깨진다.

**반영한 곳**: `Assets/_Project/Data/Units/NeutralMonster_1.asset`(spawnRangeTiles: 100→**1**) / `NeutralMonster_2.asset`(200→**100**) / `NeutralMonster_3.asset`(300→**200**). `Assets/Refresh` 후 콘솔 에러 0 확인. `NeutralMonsterSpawner`가 참조하는 에셋 자체를 고친 것이라 씬(스폰 테이블의 fileID 연결)은 건드릴 필요가 없었다.

## 23. 브랜치 분업 체계 — UI(이 PC) / PROTO(다른 PC) 병렬 작업 규약 (2026-08-05)

유저 결정: **UI 작업(전술 UI·캐릭터 생성·집결지 설정)은 이 PC의 `UI` 브랜치에서, AI 로직·건설은 다른 PC의 다른 Claude Code + 서브에이전트가 `PROTO` 브랜치에서** 병렬로 진행한다. 최종적으로 `main` 에 머지할 것을 전제로, 양쪽이 지킬 제약을 문서로 못 박았다.

### 만든 문서 3개 — **Unity 프로젝트(git 저장소) 안**의 `Docs/` 에 두었다
| 파일 | 용도 |
|---|---|
| `C:\Project\Last-Sanctuary\Docs\프로토 브렌치 준수사항.md` | 다른 PC 에이전트에게 전달할 제약·범위·git 규율 |

**왜 볼트가 아니라 git 안인가**: (1) 다른 PC 에이전트가 읽어야 하므로 GitHub 로 동기화되는 곳에 있어야 한다, (2) 이 문서가 유실되면 규약 자체가 사라지는데 볼트에는 백업이 없다(8절 9번·15절). 같은 이유로 이 `진행상황.md` 의 **읽기 전용 스냅샷**(`Docs/진행상황_스냅샷_20260805.md`)도 git 안에 두기로 했다 — 정본은 여전히 볼트의 이 파일이다.

세 문서 모두 상단에 **§0 문서 수정 규약**(임의 수정 금지 + 갱신 시 따라야 할 프롬프트)을 갖고 있다. 요지: 기존 제약을 지우거나 완화하지 말고 추가만 할 것, § 번호를 재배치하지 말 것, 소유권·씬 소유권·계약 동결 세 가지는 유저 승인 + 양쪽 문서 동시 갱신 없이는 못 바꿀 것, 갱신 이력을 남길 것.

### 핵심 제약 — 왜 이렇게 갈랐는지

**① `Assets/Scenes/Proto_01.unity` 가 38 MB 다** (320×320 타일맵이 씬에 직렬화됨). 이 파일이 머지 충돌하면 손으로 병합할 방법이 없고 한쪽 작업을 통째로 버려야 한다. 그래서:
- **씬은 `PROTO` 가 단독 소유.** UI 는 이 파일을 열어도 **저장하지 않는다.**
- **UI 는 신규 씬 `Assets/Scenes/UI_HUD.unity` 에서 additive 로 작업**하고, `[RuntimeInitializeOnLoadMethod]` 로 스스로 로드된다(Proto_01 을 건드리지 않기 위해). 씬 간 참조는 직렬화되지 않으므로 기존 싱글턴(`ResourceManager.Instance` 등) / `FindAnyObjectByType` 로 찾는다.
- `.gitattributes` 에 `*.unity binary` 를 넣어 git 이 38MB 텍스트 머지를 시도하지 않게 막는다(안전장치).
- **맵 재생성 커밋 남발 금지** — 재생성마다 38MB 파일이 전면 재작성되고 히스토리에 blob 이 영구히 쌓인다.

**② 전술 UI의 명령에 반응하는 건 AI(=PROTO의 일)** 이라서, 양쪽이 같은 자료구조를 각자 만들면 반드시 깨진다. → `Assets/_Project/Scripts/Orders/`(`TacticalTypes.cs` + `TacticalOrders.cs`)를 **계약 파일로 만들어 시드 커밋에 넣고 양쪽 모두 수정 금지로 동결**한다. UI는 `ITacticalOrderSource` 구현체를 등록만 하고, PROTO는 `TacticalOrders.For(unit)` / `TryGetRallyPoint()` 를 **null-safe 하게 읽기만** 한다(UI 씬이 없는 PROTO 쪽 PC에서도 지금과 똑같이 동작해야 한다).

**③ 파일 단위 소유권.** `Scripts/UI|Prefabs/UI|Art/UI|Art/Fonts|Data/UI` = UI, `Scripts/Combat|Units|Map|Fog|Wave|Build|Resource`·`Data/Combat|Map|Units`·`Art/Tiles|OrganicTilemap|Units`·`Tools` = PROTO. 상대 소유 파일은 읽기 전용이고, 필요한 게 있으면 `Docs/인계/` 의 요청서에 적는다.

**④ 기존 스크립트의 파일명·클래스명·네임스페이스·`.meta` GUID 불변.** 씬이 GUID로 컴포넌트를 참조하므로 개명·이동하면 상대 브랜치 씬에서 `Missing Script` 가 되고 38MB 씬을 손으로 고쳐야 한다. 직렬화 필드 삭제·개명도 금지(추가는 안전). 리팩터링은 새 파일로.
