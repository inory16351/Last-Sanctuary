## §1. 전제 — 왜 이 계획이 필요한가

| 사실 | 결과 |
|---|---|
| `Assets/Scenes/Proto_01.unity` = **38,079,617 byte (38MB) 텍스트 YAML**. 320×320 타일맵이 씬에 직렬화되어 있다 | 충돌 시 **손으로 병합 불가**. 한쪽을 통째로 버리는 것 외에 방법이 없다 → **씬 단독 소유 + 반대편 무접촉**이 계획의 핵심 |
| 저장소는 아직 작다 (packed 3.65 MiB — 씬이 압축이 잘 된다) | 하지만 씬 저장/맵 재생성 커밋마다 새 blob 이 영구히 쌓인다 → **씬 변경 최소화**, HUD 는 아예 **코드 런타임 생성** |
| 2026-08-05, **커밋 안 된 작업이 브랜치 전환/discard 로 통째로 사라진 사고** (진행상황 22절) | **단위별 즉시 커밋 + 매일 푸시** |
| `진행상황.md` 1~19절이 유실된 사고 (진행상황 15절). git 밖 볼트에 있고 백업이 없었다 | 시드 커밋에 **읽기 전용 스냅샷**을 git 안에 넣었다 |
| `진행상황.md` 요약 표가 실제 코드와 어긋나 있다 (자원 시스템·강화·유닛 선택이 이미 구현됨) | 양쪽 준수사항 §9 에 정정 표 — **중복 구현 = 충돌** |
| `core.autocrlf=true` + 작업 트리 씬이 CRLF, blob 은 LF | `.gitattributes` 에 `*.unity binary` 를 쓰면 **안 된다**(`-text` 포함 → 38MB 전체가 수정됨으로 뜬다). `-merge -diff` 만 준다 |
| 이 환경의 셸에서 GitHub 인증이 대화형이라 **에이전트가 `git push` 를 할 수 없다** | 에이전트는 커밋까지 하고 **유저가 push** 한다 |

### 작업 분담 (유저 확정, **v2 개정**)
- **UI 브랜치 (이 PC)**: HUD 전반 · **전투 AI** · 캐릭터(생성/강화/거동) · 자원 · 집결지 · **씬 소유**
- **PROTO 브랜치 (다른 PC)**: 건설(포탑) · 웨이브 규칙/구성표 · 몬스터 정의·스폰 · 맵/타일/안개 · **씬 무접촉**

**v2 개정 이유**: 전술 명령·집결지는 결국 **AI 거동을 바꾸는 기능**이라, UI와 AI가 다른 PC에 갈라져 있으면 어느 쪽도 결과를 확인할 수 없다. 두 축을 한 브랜치로 합치면서 **브랜치 간 계약(`Scripts/Orders/`)이 불필요해졌고**, 대신 템플릿 조정 빈도가 UI 쪽으로 옮겨가 **씬 소유권도 함께 넘겼다**. 폐기된 v1 설계는 §8.

## §5. 충돌 처방표

> 소유권을 지켰다면 충돌은 아래 몇 개 파일에서만 날 수 있다. 그 외에서 충돌이 났다면 **소유권 규칙이 깨진 것** — 머지를 중단하고 어느 브랜치가 남의 파일을 만졌는지 확인한 뒤 유저에게 보고할 것.

| 파일 | 처방 |
|---|---|
| `Assets/Scenes/Proto_01.unity` | **충돌하면 안 되는 파일.** `.gitattributes` 의 `-merge` 때문에 자동 병합은 시도되지 않고 "both modified" 로 멈춘다. → **`git merge --abort`** 하고 **PROTO 가 왜 이 파일을 커밋했는지** 확인. PROTO 쪽 변경이 실수라면 PROTO 브랜치에서 그 파일만 되돌린 뒤(`git checkout origin/main -- Assets/Scenes/Proto_01.unity` → 커밋) 다시 머지. **절대 눈대중으로 한쪽을 고르지 말 것** — 어느 쪽 작업이 사라지는지 알 수 없다 |
| `Docs/*.md` | 텍스트 충돌. **양쪽 내용을 모두 살려 수동 병합.** 준수사항 문서는 소유 브랜치 쪽을 기준으로 하고 상대가 추가한 내용은 갱신 이력에 남긴다 |
| `Docs/인계/*.md` | 요청서는 양쪽이 쓴다(한쪽은 본문, 한쪽은 `상태` 칸). **양쪽 내용을 모두 살릴 것** |
| `*.meta` | **GUID 를 임의로 고르지 말 것.** 원래 `main` 에 있던 파일이면 `main` 쪽 GUID 유지(씬 참조가 그걸 가리킨다). 신규 파일이면 만든 브랜치 쪽 GUID |
| 같은 이름의 신규 `.cs`/`.asset` 을 양쪽이 만든 경우 | 이름 규칙(§2) 위반. 하나를 개명하고 **씬 참조까지 포함해 모든 참조를 수정** |
| `ProjectSettings/*` | 원칙적으로 양쪽 다 안 건드리는 파일. 충돌 시 유저 판단 |

### 롤백
```bash
git merge --abort                          # 머지 진행 중
git reset --hard pre-merge-20260805        # 커밋했지만 push 전
git revert -m 1 <머지커밋해시>               # 이미 push 함 (히스토리 재작성 금지)
```
씬이 이상해졌으면 단계 4 의 물리 백업을 덮어쓴다.

## §9. 위험 요약 — 이것만 기억하면 된다

| 순위 | 위험 | 방어 |
|---:|---|---|
| 1 | **38MB 씬 충돌** → 한쪽 작업 전멸 | PROTO 는 씬을 **열어도 저장하지 않는다**. UI 도 HUD 를 코드로 만들어 씬 저장 자체를 최소화 |
| 2 | **커밋 안 한 작업이 브랜치 전환/discard 로 소멸** (실제 발생) | 단위별 즉시 커밋 · 매일 push · `reset --hard` 금지 |
| 3 | **스크립트 개명/이동으로 상대 씬의 컴포넌트가 Missing Script** | 파일명·클래스명·네임스페이스·`.meta` 불변. 리팩터링은 새 파일로 |
| 4 | **같은 기능 중복 구현** (자원 시스템 등) | 준수사항 §9 정정 표를 먼저 읽는다. **문서가 아니라 코드가 사실** |
| 5 | **`.gitattributes` 에 `binary` 를 쓰는 실수** | `binary` = `-text` 포함 → autocrlf 때문에 38MB 전체가 수정됨으로 뜬다. `-merge -diff` 만 쓸 것 (파일 안에 근거 주석 있음) |
| 6 | **맵 재생성 / 잦은 씬 저장으로 저장소 비대화** | 재생성은 UI 쪽에서 유저 확인 후 1회만, 커밋 메시지에 `[MAP]` |
| 7 | **`진행상황.md` 유실** (실제 발생) | git 안에 읽기 전용 스냅샷 유지. Write 로 밀어쓰기 금지 |
| 8 | **에이전트가 push 못 함** (인증 대화형) | 커밋까지만 하고 유저에게 push 요청. 커밋 안 하고 넘어가면 2번 위험에 노출 |
