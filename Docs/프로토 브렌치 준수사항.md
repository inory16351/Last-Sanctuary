## 🔒 §0. 문서 수정 규약 — 이 문서를 여는 모든 사람·에이전트가 먼저 읽을 것

이 문서는 참고 메모가 아니라 **두 브랜치가 서로를 깨뜨리지 않기 위해 합의한 구속력 있는 규약**이다.
**임의 수정·삭제·완화 금지.** 갱신이 필요하면 아래 프롬프트를 그대로 읽고 따를 것.

> ### 갱신 프롬프트 (이 문서를 고치려는 에이전트는 그대로 따를 것)
>
> 너는 지금 `프로토 브렌치 준수사항.md` 를 갱신하려 한다. 이 문서는 `main` 으로의 최종 머지를 **충돌 0으로** 끝내기 위한 제약 조건 명세다. 아래를 전부 지켜야 갱신한 것으로 인정된다.
>
> 1. **기존 제약을 지우거나 약화시키지 말 것.** 제약이 현실과 맞지 않으면 삭제가 아니라 "§N 은 이런 이유로 이렇게 바뀐다"를 **새 항목으로 추가**하고 원래 항목에 링크한다. (`진행상황.md` 0절 3번과 같은 원칙 — 완료·폐기된 기록도 남긴다)
> 2. **추가만 한다.** 본문의 § 번호와 순서를 재배치하지 말 것 — 짝 문서와 `머지 계획.md` 가 § 번호로 이 문서를 인용하고 있다.
> 3. **§2(파일 소유권) · §3(씬 소유권) · §4(계약 파일 동결)은 단독으로 바꿀 수 없다.** 이 셋의 변경은 **유저의 명시적 승인 + 양쪽 브랜치 문서 동시 갱신**이 있어야만 유효하다. 한쪽만 바꾸면 머지가 깨진다.
> 4. 갱신할 때마다 맨 아래 **§12 갱신 이력**에 (날짜 / 브랜치 / 무엇을 / 왜) 한 줄을 남긴다. 이력 없는 변경은 무효로 보고 되돌린다.
> 5. **작업 방향을 유지할 것.** 이 문서의 목적은 "각자 빠르게 만들기"가 아니라 **"머지 시점에 충돌 없이 합쳐지기"** 다. 편의를 위해 상대 소유 파일을 건드리는 판단은 어떤 경우에도 하지 말고, 필요하면 §7 의 요청서 경로를 쓴다.
> 6. **이 §0 규약 블록 자체는 수정 금지.**

## §2. 파일 소유권 — 이것만 지키면 머지 충돌은 사실상 0이다

원칙: **한 파일은 한 브랜치만 수정한다.** 상대 소유 파일은 **읽기 전용**이다.

Assets/_Project/Data/**                       (단, 파일 단위 소유 — 아래 참조)

### `Assets/_Project/Data/` 는 파일 단위 소유
- PROTO: `Combat/BalanceConfig.asset`, `Combat/NexusDefinition.asset`, `Map/*`, `Units/Monster_*.asset`, `Units/NeutralMonster_*.asset`, 신규 `Units/Tower_*.asset`, 신규 `Wave/WaveDefinition_*.asset`

### `ProjectSettings/` 는 원칙적으로 금지
- 예외 1: `EditorBuildSettings.asset` — **UI 브랜치가** `UI_HUD.unity` 를 등록한다. PROTO 는 건드리지 말 것.

- `ProjectSettings > Player > Run In Background` 는 **1로 켜져 있어야** 타이머가 흐른다 (진행상황 11절). 텍스트로 고쳐도 에디터 재시작 전까지 안 먹으니 UI에서 직접 확인할 것.

## §3. 씬 규칙 — 이 프로젝트에서 가장 위험한 지점

### ⚠️ `Assets/Scenes/Proto_01.unity` 는 **38 MB 텍스트 YAML 파일**이다
320×320 타일맵 데이터가 씬에 그대로 직렬화되어 있다. 이 파일이 머지 충돌을 일으키면 **손으로 해결하는 것이 사실상 불가능하고, 한쪽 작업을 통째로 버리는 것 말고는 방법이 없다.** 그래서 씬은 소유권을 나누지 않고 **PROTO 가 단독으로 갖는다.**

| 규칙 | 내용 |
|---|---|
| **P-S1** | `Proto_01.unity` 는 PROTO 만 수정·저장한다. UI 브랜치는 이 파일을 **전혀 건드리지 않는다** (UI는 별도 씬 `UI_HUD.unity` 에서 additive 로 작업 중). 따라서 이 파일에 충돌이 날 이유가 없다 — 충돌이 났다면 규칙이 깨진 것이니 즉시 유저에게 보고할 것. |
| **P-S2** | `.gitattributes` 에서 `*.unity` 는 `binary` 로 지정되어 있다. git 이 38MB 텍스트 머지를 시도하지 않게 막는 안전장치다. 이 파일을 지우거나 고치지 말 것. |
| **P-S3** | **맵 재생성(새 시드) 커밋을 남발하지 말 것.** 재생성 한 번이 38MB 파일을 전면 재작성하고, 커밋마다 새 blob(압축 후 약 1~2MB)이 히스토리에 영구히 쌓인다. 재생성이 꼭 필요하면 **한 번만** 하고 그 커밋 메시지에 `[MAP]` 을 붙여 이유를 남긴다. AI/건설 검증용으로는 기존 맵을 그대로 쓸 것. |
| **P-S4** | **씬에 새 오브젝트를 늘리기보다 프리팹으로 만들 것.** 포탑 템플릿·건설 매니저 등은 `Assets/_Project/Prefabs/Build/` 에 프리팹으로 만들고, 씬에는 프리팹 인스턴스 1개만 둔다. 씬 diff가 작아지고 나중에 UI 씬으로 옮기기도 쉽다. |
| **P-S5** | 유닛 템플릿(`Character_Template` 등)의 **인스펙터 값을 바꾸면 씬이 바뀐다.** 값 변경은 가능하지만, 왜 바꿨는지 `작업로그_PROTO.md` 에 남길 것 — 머지 후 밸런스가 달라져 보이는 원인 추적에 필요하다. |
| **P-S6** | `Templates/` 하위 오브젝트는 전부 **비활성**이어야 한다. 활성 상태로 두면 게임 시작부터 템플릿이 살아 움직인다 (진행상황 12절의 실제 사고). |
| **P-S7** | **플레이 모드에서 씬 저장은 실패한다.** 항상 `get_play_mode_status` 로 Edit mode 확인 후 저장 (진행상황 8절 5번). |

### 새 씬을 만들지 말 것
`UI_HUD.unity` 외의 새 씬은 만들지 않는다. 씬이 늘어나면 `EditorBuildSettings.asset` 을 양쪽이 건드려야 하고, additive 로딩 순서가 얽힌다.

## §4. 계약 파일 (동결) — `Assets/_Project/Scripts/Orders/`

UI 브랜치가 만드는 **전술 UI · 집결지 설정**은 결국 "플레이어의 명령"이고, 그 명령에 실제로 반응하는 건 **AI 로직(=PROTO의 일)** 이다. 양쪽이 같은 자료구조를 각자 정의하면 머지에서 반드시 깨진다. 그래서 명령의 **자료형과 접근 경로만** 미리 확정해 `main` 의 시드 커밋에 넣어두고 **양쪽 모두 수정 금지**로 동결했다.

### 계약 내용 (시드 커밋에 이미 들어있음 — 실제 파일을 읽고 확인할 것)
```
Assets/_Project/Scripts/Orders/
├── TacticalTypes.cs      enum CombatStance / BattlePosition / Doctrine,
│                         struct CharacterOrders (+ Default)
└── TacticalOrders.cs     static 접근점:
                            TacticalOrders.Source                       (UI가 등록)
                            TacticalOrders.For(CharacterUnit)           → CharacterOrders
                            TacticalOrders.TryGetRallyPoint(unit, out Vector3)
                          interface ITacticalOrderSource
```

### PROTO 가 이 계약을 다루는 방법
| 규칙 | 내용 |
|---|---|
| **P-C1** | **읽기만 한다.** `Scripts/Orders/` 안의 파일을 수정·추가·삭제하지 말 것. enum 값 하나 추가하는 것도 금지 — PROTO 쪽 `switch` 와 UI 쪽 드롭다운이 동시에 어긋난다. |
| **P-C2** | **반드시 null-safe 하게 읽을 것.** `TacticalOrders.Source` 는 UI 씬(`UI_HUD.unity`)이 로드될 때만 채워진다. PROTO 쪽 PC에는 UI 씬이 없으므로 항상 `null` 이다. `TacticalOrders.For()` 는 그 경우 `CharacterOrders.Default` 를 돌려주도록 만들어져 있으니 **그 값으로도 지금과 똑같이 동작해야 한다.** 명령이 없으면 AI가 멈추는 구현은 금지. |
| **P-C3** | 계약을 바꿔야 할 상황(값이 부족하다 등)이면 **직접 고치지 말고** `Docs/인계/API요청_PROTO→UI.md` 에 적고 유저에게 보고한다. 유저가 양쪽에 동시 반영한다. |
| **P-C4** | 집결지(`TryGetRallyPoint`)는 `CharacterBehavior` 의 목적지 선택에 **가장 높은 우선순위**로 반영한다 — 집결지가 설정된 캐릭터는 정찰·순찰을 하지 않고 그 지점으로 간다. 집결지가 없으면(`false`) 지금의 정찰/방어 로직을 그대로 쓴다. |
| **P-C5** | 전투 성향/포지션/행동 지침의 **의미 해석은 PROTO 가 정한다** (UI는 값을 넘기기만 한다). 어떻게 해석했는지 `작업로그_PROTO.md` 에 적을 것 — UI 쪽 툴팁 문구가 그 해석을 따라간다. |

## §5. 코딩 · 직렬화 제약 (이걸 어기면 상대 브랜치가 컴파일도 안 된다)

| 규칙 | 내용 |
|---|---|
| **P-D1** | **기존 스크립트 파일의 이름·클래스명·네임스페이스를 바꾸지 말 것.** 씬/프리팹은 스크립트를 `.meta` 의 GUID로 참조한다. 파일을 옮기거나 이름을 바꾸면 상대 브랜치의 씬에서 그 컴포넌트가 `Missing Script` 로 날아간다. |
| **P-D2** | **`.meta` 파일을 삭제하지 말 것.** GUID가 재발급되면 위와 같은 사고가 난다. 파일을 옮겨야 하면 `.meta` 를 반드시 같이 옮긴다. |
| **P-D3** | **UI 가 쓰는 공개 API 를 제거·개명하지 말 것.** 추가는 자유. 아래는 UI 브랜치가 실제로 호출하고 있는 것들이다 (제거 시 UI 브랜치 컴파일 실패): <br>`WaveManager`: `Phase` `WaveNumber` `PhaseRemaining` `PhaseDuration` `OnPhaseChanged` `OnWaveSpawned` `OnWaveEnded` `OnDefeat` `SkipPhase()` <br>`ResourceManager`: `Instance` `Energy` `OnEnergyChanged` `CanAfford` `TrySpend` `AddEnergy` <br>`CharacterUnit`: `Stats` `UpgradeCount` `MaxHp` `Balance` `ApplyUpgrade` `DebugSummary()` <br>`DamageableUnit`: `IsAlive` `CurrentHp` `MaxHp` `Faction` `Kind` `OnAnyDied` `OnAnyAttack` <br>`UnitCombat`: `State` `Target` `Home` `SetHome` `IsHunting` <br>`CharacterBehavior`: `Duty` `Destination` <br>`UnitSpawner`: `SpawnedNexus` `SpawnedCharacters` `SpawnOneCharacter()` `OnCharacterSpawned` <br>`MapGenerator`: `Walkable` `MapSize` `Origin` `LocalToCell` `WorldToCell` `CellCenterWorld` `CenterCell` `IsCellBlocked` `IsCellPlaceable` `SpawnGates` <br>`FogOfWarService`: `IsReady` `IsExplored` `IsVisible` `IsVisibleWorld` `ExploredPercent` <br>`CharacterUpgradeService`: `Instance` `CostFor` `CanUpgrade` `TryUpgrade` `OnUpgraded` <br>`UnitSelector`: `Instance` `Selected` `OnSelectionChanged` `Select` `Clear` |
| **P-D4** | **직렬화 필드를 삭제·개명하지 말 것.** 씬의 템플릿에 값이 직렬화되어 있다. 필드를 없애면 인스펙터에서 조정해둔 값이 조용히 사라진다. 필드 추가는 안전하다(기본값으로 채워짐). |

## §6. git 규율 — 22절 사고를 반복하지 않기 위한 것

> 2026-08-05, 커밋하지 않은 중립 몬스터 작업(스크립트 6개 + SO 3개 + 씬 변경)이 **브랜치 전환/discard 로 통째로 사라졌다.** 대화 맥락이 남아있어 겨우 복구했다 (진행상황 22절 마지막). 아래는 그 재발 방지 규칙이다.

| 규칙 | 내용 |
|---|---|
| **P-G1** | **브랜치는 `PROTO` 하나만 쓴다.** `main` 과 `UI` 는 **체크아웃조차 하지 말 것.** 다른 브랜치를 구경하려면 `git log origin/main` 처럼 원격 참조를 읽는다. |
| **P-G2** | **작업 단위마다 즉시 커밋.** 특히 씬을 만졌으면 그 자리에서 커밋한다. "나중에 한 번에" 는 금지. |
| **P-G3** | **하루 1회 이상 `git push origin PROTO`.** 푸시하지 않은 작업은 이 PC가 죽으면 없어지고, 유저가 진행상황을 볼 수도 없다. |
| **P-G4** | 커밋 메시지: `[PROTO][ADD|MOD|FIX] 한 줄 요약` (기존 히스토리 스타일 유지). 씬을 포함한 커밋은 요약에 `(씬)` 을 붙인다. |
| **P-G5** | `git reset --hard` / `git checkout -- .` / IDE의 "모든 변경사항 취소" **금지.** 되돌리고 싶으면 유저에게 물어볼 것. |
| **P-G6** | **`main` 에 직접 커밋·푸시·머지 금지.** `main` 은 머지 담당(유저 쪽 PC)만 움직인다. |
| **P-G7** | `git rebase` / `push --force` 금지. 히스토리를 고치면 UI 쪽 머지 계산이 어긋난다. |
| **P-G8** | 작업 종료 시 **`git status` 가 clean 한 상태로 남길 것.** untracked 파일이 남아있으면 다음 세션이 그게 작업물인지 쓰레기인지 알 수 없다. |

### 시작 시 1회 (다른 PC 최초 셋업)
```bash
git clone https://github.com/inory16351/Last-Sanctuary.git
cd Last-Sanctuary
git fetch origin
git checkout -B PROTO origin/PROTO
git log --oneline -3          # 시드 커밋이 맨 위에 보이는지 확인
git branch --show-current     # PROTO 인지 확인 — 매 세션 시작 시에도 확인할 것
```
`Library/` 는 git에 없으므로 첫 Unity 실행 시 임포트에 시간이 걸린다(정상).

## §9. ⚠️ 진행상황.md 요약 표가 낡았다 — 반드시 읽을 것

`진행상황.md` 15절에 기록된 **문서 유실 사고(15~19절 결번)** 때문에, 상단 "지금까지 만든 것" 요약 표가 **실제 코드와 맞지 않는다.** 표에 "❌ 미착수"로 적힌 것 중 아래는 **이미 구현되어 있다.** 다시 만들면 머지에서 정면충돌한다.

| 진행상황 표 표기 | 실제 | 파일 |
|---|---|---|
| 자원 시스템 ❌ 미착수 | ✅ **구현됨** — 에너지 풀, 몬스터 처치 획득, `TrySpend`/`CanAfford` | `Scripts/Resource/ResourceManager.cs` |
| 캐릭터 성장/생성 UI ❌ 미착수 | ✅ **강화는 구현됨** — 캐릭터별 누진 비용, 4스탯 랜덤 성장 | `Scripts/Units/CharacterUpgradeService.cs`, `Scripts/UI/UpgradeButtonUI.cs` |
| UI 전반 ❌ 미착수 | ⚠️ **부분 구현** — 유닛 선택(클릭), 에너지 라벨, 강화 버튼. 씬에 `GameSystems`/`Energy`/`Upgrade` 오브젝트 존재 | `Scripts/UI/UnitSelector.cs`, `EnergyLabel.cs`, `UpgradeButtonUI.cs` |
| (표에 없음) | ✅ 격자 경로탐색 | `Scripts/Map/GridPathfinder.cs` |
| (표에 없음) | ✅ 유기적 타일셋 + 임포터 | `Scripts/Map/OrganicTileSetSO.cs`, `Editor/OrganicTileSetImporter.cs`, `Data/Map/OrganicTileSet.asset` |
| (표에 없음) | ✅ 한글 픽셀 폰트 SDF | `Art/Fonts/NeoDunggeunmo SDF.asset`, `Scripts/Editor/NeoDunggeunmoFontBaker.cs` |

**즉 15~19절의 잃어버린 작업 내용은 "자원 시스템 + 캐릭터 강화 + 유닛 선택 + 최소 UI + 유기적 타일셋 + 경로탐색 + 한글 폰트"였던 것으로 추정된다.** 코드는 남아있고 문서만 없다.
→ **작업 전에 해당 파일들을 직접 읽어 실제 동작을 확인할 것.** 문서가 아니라 코드가 사실이다.

여전히 **정말로 미착수**인 것: `WaveDefinitionSO`(웨이브별 구성), **건설(포탑)**, 보스 전용 사이클 배율, 정비시간 초과 광폭화, 웨이브 종료 후 잔존 몬스터 정리.
